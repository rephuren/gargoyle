# gargoyle

Rack-middleware для Ruby: стоит перед веб-приложением (Rails, Sinatra, любое Rack), замечает сканеры и попытки инъекций и пишет события в JSON Lines. По желанию отдаёт приманки (`/.env`, `/.git/config`, `/wp-login.php`) с фальшивыми «ключами»: если такой ключ потом придёт в запросе, это уже не сканирование, а попытка применить украденное.

Ставьте только перед приложениями, которые вам принадлежат. Решения о блокировке принимаются по простым шаблонам и бывают ошибочными, поэтому режим по умолчанию только наблюдает.

## Быстрый старт

```ruby
# config.ru
require "gargoyle"
use Gargoyle::Middleware, mode: :monitor, log: "gargoyle.jsonl"
run MyApp
```

```bash
bundle install
bundle exec ruby bin/gargoyle demo --out demo.jsonl   # придуманный трафик, без сети
bundle exec ruby bin/gargoyle report gargoyle.jsonl [--json|--html] [--min-severity high]
bundle exec ruby bin/gargoyle rules
bundle exec rake test
```

`--min-severity` оставляет события не ниже уровня (`info`, `low`, `medium`, `high`); код возврата считается уже по ним.

Код возврата `report`: `0` событий нет, `1` есть, `2` ошибка (нет файла).

## Режимы

| режим | что делает |
|---|---|
| `:monitor` (по умолчанию) | только пишет события; ответ приложения и запрос не меняются |
| `:trap` | дополнительно отвечает сам на `/.env`, `/.git/config`, `/wp-login.php`; страницы без скриптов и ничего не повторяют из запроса |
| `:block` | дополнительно отвечает `403`, если худшая находка не ниже `block_at` (по умолчанию `:high`) |

Остальные параметры: `max_body` (сколько байт тела читать для проверки, 8192; приложение всё равно получает тело целиком), `trusted_proxies` (список адресов, от которых верится `X-Forwarded-For`; сравнение по строке, без CIDR), `on_event` (колбэк на событие), `honeytokens`.

## Правила

Десять правил: сканеры по User-Agent, пробы чувствительных путей, path traversal, SQL-инъекция, XSS, командная инъекция, Log4Shell, Shellshock, SSRF на адрес метаданных облака, фразы подмены инструкций для LLM. У каждого есть категория OWASP и техника ATT&CK. Проверка идёт по пути, строке запроса, телу, заголовкам и User-Agent; значения раскодируются из процентной записи до двух раз.

## Что пишется в журнал и чего нет

Время, адрес клиента, метод, путь и запрос (до 300 символов), User-Agent, найденные правила, категории и короткие фрагменты совпадений. **Не пишутся**: тело запроса целиком, заголовки `Authorization` и `Cookie`, пароли. Ошибка записи журнала или колбэка не роняет приложение.

## Как проверялось

- Тесты на каждое правило и на обычные запросы, которые не должны срабатывать (в том числе безобидные слова «union» и «select» в тексте), двойное кодирование, битая кодировка, 5 МБ ввода за доли секунды.
- Режимы: monitor не меняет ответ, trap отдаёт приманки и не повторяет ввод, block режет только от порога; приложение читает тело целиком; журнал без секретов; `X-Forwarded-For` только от доверенных прокси; сломанный журнал и колбэк не ломают запрос; приманочный ключ, пришедший позже, даёт находку высокой тяжести.
- Отчёт: счётчики на демо-трафике, битые строки считаются, HTML экранируется, коды возврата CLI.
- CI: Ruby 3.1, 3.3 и 3.4.

## Ограничения

- Это набор шаблонов, а не WAF. Опытный противник их обойдёт, обычный запрос иногда даст ложное срабатывание (например, текст со статьёй про SQL). Режим `:block` включайте после недели наблюдения.
- Проверено на придуманном трафике и на `Rack::MockRequest`; на реальном сайте и под нагрузкой не запускалось, задержка не измерялась. С настоящими Rails и Sinatra сборка не интегрировалась.
- Хранилище только файл JSON Lines. Нет ограничения частоты, нет учёта «очков» по адресам, нет дашборда (только отчёт).
- В приманках нет ничего настоящего: «ключи» генерируются при старте, в репозитории их нет.
